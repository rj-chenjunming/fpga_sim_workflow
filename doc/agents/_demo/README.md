# 团队演练（Dry-Run）说明 · `doc/agents/_demo/`

> **本目录是"三步流转"的一次真实演练（只编译、不仿真）**，用来验证
> `doc/AGENTS.md` 定义的团队与 `doc/skills/simenv-test/` 模板库**能否真的跑起来**。
> 它**不是**正式产物目录；通过全部门禁的用例是否移入 `TESTLIB/`，由 Lead 决定。

## 1 演练目标

验证这条链的每一环都有真实的卡点，而不是纸面流程：

```
①生成(simenv-author) → ②执行·只编译(runner) → ③验证(checker) → 整改(author) → 复编译(runner) → 复验(checker) → 守护(guardian)
   T1                      T2(卡点B)              T3(卡点C)        T5            T6(卡点B)          T7(卡点C)         T4(卡点E)
```

**这是一个"两轮"演练，不是一轮**：第一轮（T1→T3）通过了，但检查者抓到作者的 **Δ1**（收敛预算按 3 笔算、
实际 6 笔读）与 **Δ2**；于是补了整改 → 重编译 → 聚焦复验（T5→T7），复验又抓到 **Δ6**（Lead 文档里的计数不可复现）。
**"通过"不等于"没有缺陷"** —— 这正是把审查与执行分开之后才能出现的迭代。

**为什么只编译不仿真**：本工程单用例全跑实测 **≈43 分钟**；而**只编译只要 ≈2 秒**（实测 `uvlan` 1.36s + 0.86s，比值 ≈1:1300）。
演练的目的是验证**流程与卡点**，不是验证功能；编译期能抓到语法/宏/包依赖/连接错误，
这正好对应 `AGENTS.md` §2 的**卡点 B**。

## 2 演练用例与被测对象

| 项 | 值 |
|---|---|
| 用例名 | `tc_rtc_blk_reset_chk_01` |
| 目标 | `0x2000` 段 RTC I2C Master 控制器 0 的**复位值**断言 |
| 覆盖寄存器 | `i2c_scale`（块内 `0x00`）、`i2c_filter`（`0x04`）、`i2c_timeout`（`0x08`） |
| 期望复位值 | **`0x4e` / `0x7c` / `0x7c`** |
| 基准来源 | 接口文档 RTC 块**位定义表**（**不是**「寄存器汇总」表） |
| 交叉印证 | `RTL/SRC/imports/SRC/i2c_master_scheduler_top/i2c_data_ram.sv:690-692` 的 `s_init_data` |
| 驱动通道 | PCIE（`` `PCIE_SQR ``） |
| 代码落点 | `doc/agents/_demo/TESTLIB_sandbox/tc_rtc_blk_reset_chk_01.sv`（**沙箱，不进 `TESTLIB/`**） |

### 为什么选这三个寄存器

它是**本项目第 4 章「三条铁律」的教科书式样本**：

- **铁律 3**：接口文档的「寄存器汇总」表把这三个的 Reset 都写成 `0x00`，
  而同一份文档的「位定义表」写 `0x4e`/`0x7c`/`0x7c`，RTL 也是 `0x4e`/`0x7c`/`0x7c`。
  → **照汇总表写断言必然失败**。演练用它来检验"作者是否真的只认位定义表、检查者是否能独立核出这一点"。
- **铁律 2**：地址必须写成 `0x2000 + 偏移`，不能只写 `0x00`。
- **待确认点**：`0x2000` 段在接口文档里**没有任何"只能由 X 接口访问"的标注**，
  而同构的 `0x4000` DOM 段却标了"（CPU接口访问）"。
  → "没写限制 ≠ 没有限制"，选 PCIE 通道这件事必须在用例里标为待确认。
  （这一点是 `doc/_notes/06_iface_doc_regmap.md` §A.3 指出的"选通道最大盲区"）

## 3 七个任务与卡点（**两轮**：发现缺陷 → 整改 → 复验）

```
①生成           ②执行             ③验证                    整改        ②执行        ③验证          证据守护
T1 author  ──▶  T2 runner  ──▶   T3 checker  ──────────▶ T5 author ──▶ T6 runner ──▶ T7 checker ──▶ T4 guardian
  卡点A           卡点B            卡点C（通过 + Δ1/Δ2）      修 Δ1/Δ2      卡点B(v2)     聚焦复验        卡点E
```

| 任务 | 角色 | 卡点 | 产物 | 结果 |
|---|---|---|---|---|
| `task-1` | `simenv-author` | **卡点 A**：三步检索未完成不许动手 | `TESTLIB_sandbox/…v1.sv`（27459 B / 393 行） | 完成 |
| `task-2` | `simenv-runner` | **卡点 B**：只编译，rc≠0 直接退回 | `evidence/T2_compile_evidence.md` | **编译通过** |
| `task-3` | `simenv-checker` | **卡点 C**：静态复核，未过不许进全跑 | `review/T3_review.md`（39413 B） | **通过** + 抓到 **Δ1/Δ2** |
| `task-5` | `simenv-author` | —（消费卡点 C 的整改项） | 沙箱用例 **v2**（29341 B / 409 行） | 3 hunk，非注释行仅 1 行 |
| `task-6` | `simenv-runner` | **卡点 B**（v2 重跑） | `evidence/T2b_compile_evidence_v2.md` | **编译通过** |
| `task-7` | `simenv-checker` | **卡点 C**（v2 聚焦复验 + 逐字 diff） | `review/T3b_review_v2.md`（25281 B） | **通过** + 抓到 **Δ6** |
| `task-4` | `simenv-guardian` | **卡点 E**：证据不成链不算完成 | `guard/T4_guard.md`（41816 B） | **通过（成链）** |

依赖链由共享任务板的 `blocked_by` 表达：`1→2→3` 与 `5→6→7`，**` task-4` 同时阻塞于 `task-3` 与 `task-7`**
（守护必须审**最终**那条链，而不是审一半）。

### 3.1 这条链真的抓到了 3 个错

| 缺陷 | 谁的错 | 抓它的机制 |
|---|---|---|
| **Δ1**：收敛超时预算按"3 笔读"算，代码实际做 **6 笔读** ⇒ 兜底早于内层预算，一条**假失败**路径 | 用例作者 | **卡点 C** 的"**这条判据怎样才能失败**"（自查 3 遍没发现） |
| **Δ6**：`_FORMAT.md §7` 的 `10513 / 8256 / 73.7us` 三个计数**不可复现**（真实 `12200 / 8299 / 20.568us`） | **Lead（我）** | 卡点 C 第二轮**独立重算计数**；且错值 max `73.7us` **大于全集 max**，本应一眼看出 |
| **LED 模板假陷阱**："参照用例只等 `#2ms` ⇒ 等不够" —— 实际 `` `QSFP_INF.light_set `` **是阻塞式**，码流在它返回前就走完了 | 模板作者 | 模板库**事实质检**（回原文件看调用链，而不是只核格式） |

⇒ 结论：**流程的价值就是"能抓到错"**。三条错分属三个不同角色，**没有一条是靠"更小心"避免的**。
