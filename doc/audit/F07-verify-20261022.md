## 6 事件过滤与 `GET /api/runs/{id}/agents/{node}` 同口径核对

判据字符串两侧一致：

- API（[api.py:283](../../loop/services/api.py#L283)）：
  `if event.get('node') == node or str(event.get('node', '')).startswith(node + '_')`
- 脚本（[measure_agent_read.py:67](../../loop/spikes/measure_agent_read.py#L67)）：
  `if event.get("node") == NODE or str(event.get("node", "")).startswith(NODE + "_")`

两处偏差（实测）：

1. **坏行行为不同**：API 走 `ProgressLog.read()`，坏行 `continue` 跳过；脚本直接 `json.loads`
   抛出。探针在事件文件中追加一行 `{not json}` 后：

   ```
   script on malformed line: JSONDecodeError
   ProgressLog.read on same file: 100 events (skips malformed)
   ```

   进程被 SIGKILL 时 JSONL 尾部出现半行是现实场景，届时测量脚本会整体崩掉（而不是少一条事件）。
2. **响应体口径偏小**：脚本的 `response_bytes` 只序列化 `read_view` + `events`，
   API 还会加 `capabilities` 与 `context_budget`（[api.py:288](../../loop/services/api.py#L288)）。
   medium 档实测：

   ```
   script response_bytes: 59148
   API-shaped response_bytes: 59309
   delta: 161
   ```

   偏差 161 B 不影响 1 MiB 阈值判断，但「响应体字节」不是 API 响应的真实字节数。

## 7 原必改 1（已由 `9ebee73` 整改）：`cpu_ms_per_read` 口径错误（自相矛盾）

代码（`6c4ee6e` 版本第 99 行；整改后为 [第 85/103 行](../../loop/spikes/measure_agent_read.py#L85)）：

```python
"cpu_ms_per_read": round(time.process_time() * 1000.0 / max(1, repeat), 3),
```

`time.process_time()` 是**进程启动至今**的累计 CPU，不是本次循环的增量；它包含三档样本构造
（大量 `O_EXCL`+`fsync` 写）以及前面档位的全部读取与哈希。于是：

| 样本 | CPU/读（HEAD r20） | wall median（HEAD r20） | CPU 是否 > wall |
|---|---|---|---|
| small | 8.315 ms | 4.104 ms | 是（构造样本被摊入） |
| medium | 40.500 ms | 31.971 ms | 是 |
| large | 288.048 ms | 241.100 ms | **是**（差 47 ms） |

`--repeat 5` 时 large 为 343.267 ms vs wall 254.950 ms；`doc/STATUS.md` §30 自己记录的
228.291 ms 也 > 184.149 ms。单线程脚本里「每次读取的 CPU」不可能超过该次 wall，故该列不可用。

修法（一行）：读取前后各取一次 `time.process_time()`，累加增量后除以 `repeat`；或把列名改成
「进程累计 CPU / repeat」并明确不参与阈值判断。
