## 1 结论

**建议合并（附 2 项证据口径必改；代码层未发现阻断性缺陷）。** 能力四维只由 `services/agent_view.py` 投影，API 与 Agent 窗口同源，前端只剩 `web/capabilities.js` 一套格式化；F16 的闭锁未调用 provider、整请求 `check_budget`、聚合预算错误消息三条断言均能真实证伪，且本切片未改预算/闭锁/红线路径。

判定依据：

- **能力单一来源成立**：`_capabilities` 全仓只有一处定义（`services/agent_view.py:143`）；`node_capabilities` 复用 `_collect`/`_status`/`_capabilities`；`build_agents` 与 `node_capabilities` 是仅有的两处消费；API 只调用 `node_capabilities`，没有在 API/前端另算。

## 3 建议项

1. **历史 attempt 的 `execution` 语义需在规格中钉死（当前取节点最新 mode，不随 `?attempt=` 变化）。**
   `agent_window` 把全部事件交给 `node_capabilities`；`_collect` 的 `state.mode` 取最后一个带 `mode` 的事件。实测：先 standin 再 live 的 N8 事件序列，`node_capabilities("N8", events)` 返回 `execution: "real"`。窗口支持 `?attempt=<sequence>`；若用户选中 standin 的 attempt 1，而同屏 `awModel` 显示「替身 / 未配置模型」，能力行却会显示「本次 真实」。当前规格没有定义 capabilities 是「节点级最新事实」还是「所选 attempt 的事实」。建议二选一：
   - 在 `AGENT_WINDOW_SPEC.md`/`WEB_UI_SPEC.md` 明确「能力事实是节点级事实，不随 attempt 变化」，并在窗口把「本次」改成「本节点最近一次」等无歧义文案；
   - 或按 attempt 过滤事件（需要 `N8_request` 事件带 attempt 边界/序号），让能力行与所选请求一致。

2. **补一条使用真实事件形状的能力用例。**
   现有 `test_node_capabilities_equal_role_card_projection` / `test_agent_window_api_returns_same_capabilities` 手工把 `{"mode": "standin"}` 放在 `N8` 的 `node_finished.detail` 上；真实代码是在 `N8_request` 的 `node_finished.detail` 里写 `mode`（`workflows/chunks/model_steps.py` 的 `_run_model_attempt`）。当前实现用 `_collect` 的 `_base_node` 归一后实测两种形状都能得到 `standin`（本报告 §4.4 有真实形状实测），但测试没有钉住这条真实路径；若未来有人把 `agent_window` 的 `_collect` 输入改成只传过滤后的精确节点事件，测试不会报警。

3. **API 用例的期望值建议改为精确 dict，而不是再调用同一个被测函数。**
   `test_agent_window_api_returns_same_capabilities` 现在断言 `body["capabilities"] == A.node_capabilities("N3", events)`；两侧调用同一实现，若该实现本身错，测试会同错同过。建议至少对 `implemented is True`、`execution == "standin"`、`dependencies_ready is None`、`verification_scope is None` 做逐字段断言（对照 `build_agents` 的角色卡断言已经这样做了）。

4. **`app.js` 对 `window.Capabilities` 没有存在性 guard。**
   `web/app.js:1455` 直接调用 `window.Capabilities.line(...)`；`agent-window.js` 有 `window.Capabilities ? ... : ""`。若 `capabilities.js` 因缓存/部署缺失，角色卡渲染会抛错，可能中断运行视图。建议与窗口一致做 fallback（或至少在 `app.js` 顶部做一次显式检查）。

5. **前端「唯一实现」测试可再收紧。**
   `test_frontend_has_one_formatter_and_both_consumers_use_it` 只断言 `app.js` 不含 `function capabilityLine`；若第二套实现改名（如 `capsLine`）或直接内联「能力 实现 …」字符串，测试不会发现。建议同时断言 `app.js`/`agent-window.js` 不含 `"能力 实现"` 文案，与全仓 grep 的口径一致。

6. **聚合预算错误消息的测试可再锁一层格式。**
   `test_unlocatable_change_fails_closed` 现在只断言 `"tc_big.sv" in message`；实测消息为 `...（tc_big.sv(5004)；不得静默抽样或丢文件）`。建议加断言 `"(5004)"` 或 `"tc_big.sv("`，把「文件名 + 最小成本」这一新增诊断格式固定下来，防止以后只剩文件名。
