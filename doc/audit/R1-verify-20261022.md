## 3 规格条款与逐条判读

规格原文（`doc/spec/AGENT_CONTEXT_SPEC.md:81-90`）：

> **原子发布（R1，2026-10-22）**：数据与校验和都不得在最终文件名上边写边暴露。发布流程固定为：
> ① 在**同一目录**写私有临时件（名字不以 `request.json`/`result.json`/`.sha256` 结尾，不参与读取扫描）；
> ② `fsync` 临时件内容；③ 以**不可覆盖**的原子操作（同文件系统 `os.link`/等价语义）发布到最终名，
> 再删除临时件；④ 同步目录项。发布顺序固定为 **数据 → 校验和**。任一时刻被终止，最终名下只可能
> 「不存在」或「完整」，**不会出现空的或半截的 `.sha256`**。
> - `seal_record` 仍是唯一发布点；竞争写同一编号只有一个成功，失败者不得覆盖已发布的件。
> - 进程终止保证；断电/掉电下的持久性不在本契约声称范围（需另测）。
> - 半件（`incomplete`）只报告状态、不消费；已有 `committed` 尝试照常可读；真正的 `corrupt`
>   （内容与校验不符/JSON 坏，无法由进程终止解释）仍显式失败，不得靠「一律当 incomplete」掩盖篡改。

### 4.3 实现 diff 核心（`git show 907697e -- loop/host/agent_memory.py`）

```python
def _sync_directory(folder: Path) -> None:
    """同步目录项；不承诺断电持久性（R1 契约只承诺进程终止）。"""
    fd = os.open(folder, os.O_RDONLY)
    try:
        os.fsync(fd)
    finally:
        os.close(fd)


def _write_once(path: Path, content: bytes) -> None:
    path = Path(path)
    folder = path.parent
    fd, temp_name = tempfile.mkstemp(prefix=".publish-", suffix=".tmp", dir=folder)
    temp = Path(temp_name)
    try:
        with os.fdopen(fd, "wb") as stream:
            stream.write(content)
            stream.flush()
            os.fchmod(stream.fileno(), 0o400)
            os.fsync(stream.fileno())
        os.link(temp, path)  # 不可覆盖：已发布的同名记录绝不被改写
    finally:
        with contextlib.suppress(OSError):
            temp.unlink()
        _sync_directory(folder)


def seal_record(path: Path, value: Any) -> None:
    """公开封存接口：写数据 + 校验和（唯一发布点；顺序固定 数据 → 校验和）。"""
    content = encoded(value)
    _write_once(path, content)
    _write_once(path.with_suffix(".sha256"), hashlib.sha256(content).hexdigest().encode("ascii"))
```

## 5 问题（均非阻断）

### P3-1 R1-A 列举的「校验临时件创建/部分写入」故障点没有专门用例

计划 R1-A 原文列出「数据写入、校验临时件创建/部分写入、发布前后」逐个固定故障点。套件覆盖了：数据临时件半写（:103）、数据已发布/校验未发布（:71）、两者已发布（:139），但**没有**单独把「第二次 `_write_once` 的临时件只写一半时终止」作为一个用例。可观察状态与 :71 等价（数据已发布、校验不存在 ⇒ `incomplete`），且两个文件走同一个 `_write_once`，所以不构成行为缺口；建议在下次触碰该文件时补一条对称用例，让 R1-A 的枚举逐点可追溯。

### P3-2 定点用例与实现机制耦合（`os.link`/`os.fsync` monkeypatch）

:71/:103/:139 在子进程里替换 `os.link`/`os.fsync` 再 `os._exit(9)`。因此它们证明的是**协议一致性**（必须用 `link` 发布），而不是在机制无关意义上证明不变量；若将来改用规格允许的「等价语义」实现（而测试未同步），用例会红而不变量仍成立。规格已点名 `os.link`/等价语义，故可接受；但审阅者应知道这三条不是机制无关证据——机制无关的那部分由 §4.5 的随机终止探针覆盖（本次已验证）。

### P3-3 并发用例不具区分力，且缺「已发布件再写」的顺序断言

`test_concurrent_seal_...` 在**父提交**树上也通过（§4.1 输出 `.FFF.......` 的第 5 个点即该用例）：旧实现的 `O_CREAT|O_EXCL` 本来就保证「恰好一个成功」。它是有效的回归护栏，但不能作为「缺陷已修」的独立证据（我在 §4.7 用顺序重写 + 8 进程竞争另行验证了「不覆盖」）。套件内没有「先封存成功、再一次 `seal_record` 必须失败且内容逐字不变」的用例；建议补，成本低。

### P3-4 终止残留 `.publish-*.tmp` 无清理策略

大载荷探针 10 次终止中 6 次留下 1 个 `.publish-*` 临时件（4 MB 内容），不参与读取、不影响状态判定，但长期运行的记录循环会累积磁盘占用（压力用例的循环上限是 2000 次尝试，虽在 0.35 s 即被终止，仍是可放大该残留的写法）。规格未要求清理，建议登记一条诊断/清理口径（例如读取侧忽略 + 运维可安全删除），避免把临时件误当证据。

### P4-1 `_sync_directory` 在 `finally` 中未捕获异常，可能覆盖原始错误

若目录 `os.open`/`os.fsync` 失败（权限、目录被删），`finally` 抛出的异常会替换掉主流程的原始异常（例如 `FileExistsError` 或写盘错误），错误归因变差。不影响发布不变量（最终名此时仍只可能 absent/完整），属可观测性小瑕疵。

### P4-2 「数据缺失、校验存在」仍判 `absent`（父提交既有，R1 未改变）

`record_state` 先判 `not path.is_file()` 返回 `absent`，不检查 `.sha256` 是否存在；删除数据文件、保留校验的篡改会被报告为 `absent`（`read_view` 再映射为 `incomplete`），而不是显式安全信号。新协议下该状态不可由发布产生，且不在 R1 变更面；记录为残留语义，供后续切片决定是否收紧。
