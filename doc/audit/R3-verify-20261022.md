## 5 逐项契约核对（读码 + 独立探针）

### 5.1 `UnicodeDecodeError` 是否归入**该条** errors、是否改写输入语义

实现（[baseline.py:185-196](../../loop/host/baseline.py#L185-L196)）：

```python
try:
    text = manifest_path.read_text(encoding="utf-8")
except UnicodeDecodeError as exc:
    errors.append(f"{MANIFEST} 编码不是 UTF-8（解码失败）：{type(exc).__name__}: {exc}")
    return record
except OSError as exc:
    errors.append(f"{MANIFEST} 无法读取：{type(exc).__name__}: {exc}")
    return record
try:
    doc = json.loads(text)
except json.JSONDecodeError as exc:
    errors.append(f"{MANIFEST} 无法解析：{type(exc).__name__}: {exc}")
    return record
```

- 解码失败 `return record`（`valid` 初始为 `False`），不进入任何 artifact 校验，不写 `missing`。
- 全仓 `loop/host|services|workflows` 无 `errors="ignore"`/`errors="replace"` 用于 **manifest**；
  仅 `baseline.py:190` 注释提到 `errors="ignore"`，属说明文字。
- **反证探针**：把合法 manifest 中一个空白双字节替换为 `0xff`（其余 JSON 结构不变）。

```
CASE3 original bytes decode-ok: True
CASE3 mutated bytes are non-UTF-8; ignore-decoded text parses as JSON: True
CASE3 inspect valid= False errors= ["manifest.json 编码不是 UTF-8（解码失败）：UnicodeDecodeError:
        'utf-8' codec can't decode byte 0xff in position 238: invalid start byte"]
```

即：若用 `errors="ignore"` 改写再解析，这份清单会变成「可解析的合法 JSON」而被放行；实现选择了
`valid=false`，证明**未改写输入语义**。

### 5.2 列表端点：坏件 `valid=false`、同目录好基线仍在

`GET /api/baselines`（[api.py:78](../../loop/services/api.py#L78)）直接消费
`config_api.list_baselines` → `host.baseline.list_baselines`（[baseline.py:296](../../loop/host/baseline.py#L296)），
逐条 `inspect` 后组装，单条异常不再冒出。


### 5.3 real 创建：结构化拒绝 + 零副作用

`details["missing"] == []`、`errors` 非空、run/作业/事件目录条目零变化，符合 R3-A。

## 7 发现的问题

### 阻断项

**无（0 个）。**

### 非阻断（P3，建议，不影响本次合并）

1. **P3-1「坏 JSON」回归无专门用例。** 计划 R3-A 明确要求「保持数组/空对象/**坏 JSON**/缺文件的原回归」。
   仓库中「坏 JSON」只有 `{}`（空对象）与 `[]`（数组），没有 `manifest.json` 为语法非法 JSON 的用例。
   本轮探针确认行为未变（`无法解析：JSONDecodeError` + `valid=False`），实现上该分支也未改动；
   但建议补一条不读源码即可判定的断言，避免后续改动静默破坏该分支。
2. **P3-2 API 层零副作用是代理断言。** `test_non_utf8_manifest_real_start_is_rejected_with_structured_errors`
   只断言 `prepare_run_dir` 不被调用，未快照 run/作业/事件；同语义的快照断言在单元层用例里有
   （`_state_snapshot`）。当前实现下准入在 `start` 最前端，风险低；作为覆盖建议记录，非缺陷。

### 观察（不计为问题）

- `test_api_baseline_detail.py` 通过 `from test_baseline_admission import make_baseline` 复用夹具，
  依赖 pytest rootdir 的 `sys.path` 注入；已实测单文件运行 `5 passed`，在仓库既定命令下可用。
- `96e9705` 顺带把「manifest 读取 OSError」的错误文案从「无法解析」改为「无法读取」。这是更准确的
  诊断，仓库无测试依赖旧文案，未造成回归。
