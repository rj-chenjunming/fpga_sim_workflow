## 3 规格条款（原文要点）

[AGENT_CONTEXT_SPEC C1](../spec/AGENT_CONTEXT_SPEC.md#L40)：

> **预算计量的唯一 owner 是 Host（R5，2026-10-22）**：准入检查与对外展示使用**同一次测量**——
> `AM` 的紧凑序列化总量，构成包含外层键名与标点。API 下发该总量、各计费字段字节与**显式序列化开销**，
> 且满足 `分项之和 + 开销 == 总量`；窗口只消费这些数字，不得另写求和/占比判据（红线 8）。
> `offered`/`scope` 等**未发送**给模型的材料若要展示，必须单列为「记录存储大小」，不计入预算；
> 上限未知时显示未知，不给假比例；token 仍为 `unknown`。

[AGENT_WINDOW_SPEC「可解释性」1](../spec/AGENT_WINDOW_SPEC.md#L57)：`context_budget` 由 Host 下发实际计费测量
（总量与 `AM.check_budget` 同一实现）、计费字段字节、显式开销与上限；`分项之和 + 开销 == 总量`，
总量与 Host 准入字节**完全相同**；窗口不另做求和/占比/上限判断；旧记录由 Host 同一算法重算，无法确定保持 unknown；
未知 token 显示「未知（未测量）」；上限未知不显示比例。

验收 R5-A（[计划](../plans/2026-10-22-next-iteration-specdd.md#L75)）：Host 准入字节与 API/UI 总量完全相同；
空值、中文、转义、外层键名/标点和人工指令覆盖；分项加显式开销等于总量；上限未知不显示假比例，token 仍 unknown。

### 4.2 E2 前端是否真的没有第二套判据

代码审查 + node 纯函数实测（`loop/web/context-explain.js`、`loop/web/agent-window.js`）：

1. `budget(measure)`（context-explain.js:46）只读取 Host 下发的
   `measured / used_bytes / breakdown / overhead_bytes / limit_bytes / used_percent / storage`；
   `totalBytes` 直接取 `used_bytes`，`overheadBytes` 取 `overhead_bytes`，`usedPercent` 取 `used_percent`，
   无任何 `bytes` 加法、无 `/ limit` 除法、无 `> limit` 比较。
2. `BILLED`（context-explain.js:17）只是**展示顺序**；行数据来自 `breakdown` 的键值（Host 数值），
   不是对记录字段重新编码。行的 `percent` 已删除。
3. `jsonBytes()` 仍存在，但仅用于 `inputDiff()` 的输入顶层字段字节变化（F11 的一半），不参与预算。
   用注释剥离后的源码检查：`FIELDS` / `total +=` / `jsonBytes(request[` 均不在代码中；
   `offered` 在代码中出现的位置只有 `function storage` 之后的 `offered_bytes` 读取。
4. `agent-window.js:132` 只调用 `X.budget(view.context_budget)`，不传记录、不自算；
   展示行「合计（Host 计费）」「其中序列化开销（键名/标点）」「上限/使用率」全部来自 `b.*`；
   `offered/scope` 单独一行「记录存储大小（不计费）」；`measured=false` 时显示
   「预算构成: 未知（该记录没有可重算的计费材料，Host 不估算）」、摘要「未知（未测量）」；
   token 固定「未知（未测量）」。上限未知时该行显示「上限: 未知 · 使用率: 未知」。
5. `web/` 其它文件没有预算判据：全目录 grep `budget|limit_bytes|totalBytes|使用率|percent`，
   命中只在 `context-explain.js` 与 `agent-window.js`；没有第二处 `120000` 常量或上限比较。
6. 无记录（`!request`）分支不调用 `budget()`，只显示「无请求记录」——不会拿空记录冒充 0。

## 5 问题（均为 P3，非阻断）

**P3-1 字段集合在两处隐式重复，未来扩字段会静默漂移。**
`loop/host/agent_memory.py:99` 定义 `BILLING_FIELDS = ("info","instruct","schema")`，`context_budget`
只用这三个键重算；而准入 `loop/workflows/chunks/model_request.py:136` 传的是 `request_contract()` 的**完整**
contract（当前恰好只有 `info/instruct/schema`）。若未来 contract 增加第 4 个键，准入会计入而展示/重算不计入，
违反「完全相同」。建议让 `measure_budget` 自己定义并校验契约键集（或 `context_budget` 用同一常量断言
`set(contract) == BILLING_FIELDS`），避免两套字段集；窗口的 `BILLED` 只是展示顺序，不参与口径。
*当前无缺陷*：`request_contract()` 只有三个键，实测四条链路口径一致。

**P3-2 展示是「事后重算」，记录里没有持久化准入总量。**
`context_budget` 从封存记录用当前算法重算，未读取（也不存在）准入时落盘的 `used_bytes`。当前算法确定，
所以历史记录显示值与当时准入值相同（§4.1 已数值验证）；但若将来改序列化算法，旧记录的窗口数字会变，
不再是当时实际准入的值。规格允许「旧记录由 Host 用同一算法重算」，故不构成违约。若需要历史可审计，
建议在只增记录中追加 `used_bytes`/算法版本字段，或把计量算法版本化。

**P3-3 「无第二套判据」的代码文本断言强度有限。**
`loop/tests/test_context_explain.py:162` 只 grep `FIELDS`/`total +=`/`jsonBytes(request[`/`offered` 四个 token；
它证明不了「运行时不会出现第二套推导」。真正的证据是 §4.2 的行为断言（行/总量/开销只随 Host 数值变化）
与本次独立探针。后续若继续收敛，建议再加一条行为用例：向 `C.budget` 喂入 `used_bytes` 与分项之和不等的
Host 测量，断言 `totalBytes` 仍等于 `used_bytes`（现有用例已部分隐含此点）。

**P3-4 新展示文案没有 DOM/浏览器断言。**
`tests/browser/` 与 `test_web_smoke.py` 都没有 budget 文案/比例断言；新行（合计/开销/记录存储大小/token 未知）
只由纯函数结果与接线字符串间接证明。属覆盖缺口，不是本实现缺陷；若要声称「窗口显示」已完成验收，需要一次
真实浏览器渲染（见 §6）。
