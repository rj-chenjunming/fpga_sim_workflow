## 0 先决事实（P3 判据成立的前提，全部实测）

1. **sandbox 的可写边界 = 会话创建时的 cwd（`SessionHeader.cwd`，即启动目录）。** 实测：`session-*.ndjson` 的
   `{"type":"session","cwd":…}` 与 `pwd` 都是启动目录 `…/workcopy`；`workspace-write` 档下副本内可写、副本外拒绝（§1.4）。
   官方文档同向（`dsh-sandbox-policy`：「Normal agent calls use the session's immutable cwd」；`workspaceRoot` 仅为
   "agentless 调用或无 cwd 的会话"兜底），**但本探针两跑里 `workspaceRoot` 默认值 = `process.cwd()` = 同一目录，没有单独隔离验证
   「cwd 与 workspaceRoot 冲突时谁赢」**——留作实现期一条补充验证；对本计划的结论无影响，因为配方是 `cd <副本>` 再起进程。
   另实测 `--patch` 的 config 是**整块替换**而非深合并：打了 `- id: sandbox-policy` 后 dump 里默认的 `workspaceRoot` 行直接消失。
2. **真正决定档位的是 `permission-presets.defaultPreset`（用户层），而不是 `sandbox-policy.mode`。**
   只 `--patch` 把 `sandbox-policy.mode` 设成 `read-only`，会话初始化事件仍然是 `danger-full-access`（见 §1 P3-A）。
   根因链（三段都是可复核的实测，迁移代码路径未逐行核对，标注为推断）：
   a. 宿主 `~/.dsh/settings.yaml` 第 87–88 行有 `permission:` / `defaultPreset: danger-full-access`（实测 grep）；
   b. 按 BRIEF §1a 复制该文件进探针 home 后，探针 home 的用户层
      `profiles/headless/cordis.patch.yml` 里出现 `- id: permission … defaultPreset: danger-full-access`（实测 cat）——
      **推断**：由 dsh 启动引导从 `settings.yaml` 迁移而来（home 内有 `settings.yaml.imported` 迁移痕迹）；
   c. 佐证时序：首次 headless 启动**之前**的 dump（13:56，`dump-config-headless.yml`）无 `defaultPreset`；
      启动引导之后同一命令 dump 的第 238 行出现 `defaultPreset: danger-full-access`（实测）。
   该用户层值在会话初始化时覆盖 bundle 的 `sandbox-policy.mode`。
3. **两档都只约束"写"，不约束"读"。** bwrap 档位 = `--ro-bind / /`（整机只读挂载）+ workspace-write 时才额外 bind 可写副本，
   所以模型对宿主任意可读文件（含 `~/.dsh/settings.yaml`、进而 `~/.dsh/.credentials.yaml`）都能 `rc=0` 读到。
4. 会话存储按 cwd 分目录：`DSH_HOME/sessions/--<cwd 转义>--/session-<id>/session.v4.jsonl.zstd`，
   运行时上下文快照（含 `sandbox:policy` 段）与 `permission/preset`、`sandbox/mode`、`approval/policy` 事件都在里面，可机器可判。

### 1.6 P3 结论（三态：**部分**）

| §6.1 P3 判据 | 实测 | 态 |
|---|---|---|
| cwd 绝对路径且被约束在 attempt 副本内 | `pwd` = `.../p3p5/workcopy`；`session.cwd` 同值；切 cwd 不放宽写权 | **过** |
| 越界 `write` 被拒 | read-only 与 workspace-write 两档均 `rc=1` + `Read-only file system`；外部 shell 无文件 | **过** |
| 越界 `read` 被拒 | **未拒**：`AGENTS.md`、`~/.dsh/settings.yaml` 两档都 `rc=0` | **不过** |
| 档位可被 `--patch` 控制 | 只钉 `sandbox-policy.mode` **无效**（被用户层 `permission.defaultPreset` 覆盖）；必须同时钉 `permission.defaultPreset` | **部分** |
| 相对路径落在副本内 | `echo > inside-write.txt`、`> sub/nested2.txt` 落在 `workcopy/` 下 | **过** |

**对规格的含义（§6.1 P3 / §7 Q 组、目标态 #11）**

1. **判据要改**：P3 原判据「越界 read 被拒」在当前实现下不可能满足——bwrap 档位只给整机 ro 挂载 + 副本可写 bind。
   隔离承诺必须收窄成「**写**隔离」：能写=副本（或只读），**读是全机透明的**。
   由此推论：`~/.dsh/.credentials.yaml` 对 attempt 内模型可读 ⇒ **attempt home 绝不能放凭据**，且模型输出/会话日志存在密钥入档风险，需在 SPEC 里写"凭据不可进模型可读路径"或"独立注入"。
2. **执行器契约要写死两条前置**（否则探针"通过"是假的）：
   ① 每 attempt 进程必须以 `cwd=<副本绝对路径>` 启动（唯一实测有效的做法；把边界寄望于
   `sandbox-policy.workspaceRoot` 配置不可靠——文档称其仅为无 cwd 时的兜底，本探针未单独隔离验证该优先级）；
   ② 必须显式钉 `permission-presets.defaultPreset`（`read-only` / `workspace-write`），**禁止**继承宿主 `settings.yaml` 的 `danger-full-access`。
3. 退出通道：切 working directory 不越界，可放心允许模型在副本内切目录；但"相对路径 = 相对当前 cwd"，投影/证据里要记 `session.cwd` 与启动 cwd 两个值。

## 2 P5：kill -TERM/-KILL 父进程后，工具子孙是否残留

### 2.1 命令（原样；`run-p5.sh`，一次 bash 调用内完成"起→等工具子进程→杀→快照→自证"）

```bash
# 用法：run-p5.sh <tag> <pid|pgid|kill9> <patch-file>
TASK='请调用一次 bash 工具执行 sleep 45，等它结束后只回复 DONE'
DSH_HOME="$H" $N $DSH --profile headless --patch patch-public.yml --patch "$S/$PATCHFILE" --json "$TASK" &
LAUNCH_PID=$!
# 等 NDJSON 出现 tool_call，再递归 pgrep -P 等 launcher 的子孙里出现 "sleep 45"
tree() { local p=$1; [ -z "$p" ] && return 0; echo "$p"; for c in $(pgrep -P "$p"); do tree "$c"; done; }
kill -TERM "$LAUNCH_PID"          # 或 kill -KILL / kill -TERM -- -$PGID
wait "$LAUNCH_PID"; echo "headless_exit=$?"      # +3s / +8s 各快照一次子孙与全命名空间
```

### 2.2 2×2 矩阵（档位 × 信号）

| 档位 \ 信号 | `kill -TERM`（只杀 dsh 父进程） | `kill -KILL`（SIGKILL） |
|---|---|---|
| workspace-write（bwrap `--die-with-parent`） | 无残留，`headless_exit=0` | 无残留，`headless_exit=137` |
| danger-full-access（**无 bwrap**） | 无残留，`headless_exit=0` | **残留 `sleep 45`**（+3s、+8s 仍在；`headless_exit=137`） |

杀前子孙树（workspace-write 档，`p5/kill-pid-during.txt`）：

```text
     15       3       0 Sl   /home/soft/DSH/node/bin/node .../dsh/lib/bin.js --profile headless ...
     45      15      45 Ss   bwrap --ro-bind / / --dev /dev --unshare-pid --proc /proc --die-with-parent --tmpfs /tmp --bind .../workcopy .../workcopy -- bash -c sleep 45; echo "sleep result: $?"
     46      45      45 S    bwrap --ro-bind / / ... -- bash -c sleep 45; echo "sleep result: $?"
     47      46      45 S    bash -c sleep 45; echo "sleep result: $?"
     48      47      45 S    sleep 45
```

TERM 之后（`p5/kill-pid-after3s.txt` / `after8s.txt`，两次都是）：

```text
# launcher 及其子孙进程树 (pid ppid pgid stat args)
# 全命名空间: 非本探针但仍匹配 sleep 45 的进程
(无)
```

SIGKILL + danger-full-access 之后（`p5/kill9-dfa-after8s.txt`）——**残留**：

```text
# launcher 及其子孙进程树 (pid ppid pgid stat args)
# 全命名空间: 非本探针但仍匹配 sleep 45 的进程
     42 sleep 45
```

同一次运行的杀前树只有两层（可见无 bwrap 干净执行）：

```text
     15      15 …  node .../bin.js --profile headless …
     42      15      42 Ss   sleep 45          ← 工具子进程直接挂在 node 下，无 --die-with-parent
```

终态与退出码：

```text
kill -TERM 15  →  headless_exit=0       # 注意：0！
kill -KILL 15  →  headless_exit=137
```

TERM 场景的 NDJSON 尾部（`p5/kill-pid.ndjson`）——**有 `final`（空串）、无 `turn_end`、无 `tool_result`**：

```json
{"type":"session","sessionId":"session-24b2c8d4-…","cwd":".../workcopy"}
{"type":"status","phase":"turn_start","turn":1}
{"type":"status","phase":"step_start","turn":1,"step":1}
{"type":"tool_call","callId":"call_00_MFLJ…","tool":"bash","input":{"command":"sleep 45; echo \"sleep result: $?\"","timeoutMs":90000}}
{"type":"final","text":""}
```

### 2.3 P5 结论（三态：**部分**）

- **子孙清理**：`kill -TERM` 两档都干净（TERM 后 3s/8s 子孙与全命名空间均无 `sleep 45`）→ **过**。
- **`kill -KILL` 在无 bwrap 档（danger-full-access）残留工具子进程** → **不过**（残留 = 按 §6.1 P5 判据算失败）。
- **退出码不可用作判据**：TERM 后 `headless_exit=0` 且 NDJSON 有 `final`（空）却无 `turn_end`
  → **"被终止"与"正常完成"在退出码/终态上不可区分** → 收口必须靠 `turn_end`/提交工具证据，不能靠 exit code。

**对规格的含义（§6.1 P5 / 目标态 #11 的 terminate 契约）**

1. terminate 契约要写成三步且**顺序固定**：先 `SIGTERM`（dsh 会 abort 在跑的工具、子进程随 bwrap `--die-with-parent` 一起收）；
   超时后 `SIGKILL` **整个进程组**（`kill -TERM -- -PGID` / 起进程时 `setsid` 独立进程组）——
   因为一旦档位退化成 danger-full-access（无 bwrap 兜底），只杀父 pid 会留下孤儿工具进程。
2. Host 不得把 `exit code 0` 当"attempt 成功"：必须要求 `turn_end`（`reason.kind`）+ `submit_result` 证据；
   `final.text=""` + 缺 `turn_end` 要显式判 `terminated/aborted`。
3. 探针还顺带证明：`pgrep -af 'sleep 45'` 这类**按任务文本匹配**的写法会把 launcher 自己（argv 含任务文本）算进去，误判"子进程在跑"；
   正确判据是沿 `pgrep -P` 往下走子孙链（本报告用法）。这条要写进实现期自检脚本，不然"清理干净"会自证失败。

## 4 清理与自证

- 每次 kill 实验收尾都 `pkill -TERM -f 'sleep 45'` + `pkill -TERM -f "slots/p3p5/<patch>"`，然后：
  `pgrep -af 'sleep 45'` ⇒ `(无匹配)`；`pgrep -af 'slots/p3p5/<patch>'` ⇒ `(无匹配)`。
- **没碰 GUI**：清理只用本探针特征（槽内 patch 文件名 / `sleep 45`），未使用 `pkill node`、未按 `bin.js` 通杀。
- **观察边界（必须写明）**：探针的 bash 工具本身跑在 bwrap `--unshare-pid` 里，`pgrep/ps` 只能看本 PID 命名空间；
  命名空间内 `--die-with-parent` 保证本次调用结束后不会有跨调用的残留进程。因此置信度最高的是「同一命名空间内的 +3s/+8s 快照」，
  本报告结论均基于它；不能说"已用 `pgrep` 证明全机无残留"。
- `~/.dsh` 零写入；未写 `loop/`、`kb/`、`doc/`；只写 `slots/p3p5/` 与本文件。
