# P6 子 agent：`subagent.started/finished` 通知 + 越额拒绝

## 假设

sdk/headless profile 已挂 `subagent`+`tool-subagent`：模型能 spawn 子 agent；子 agent 生命周期**有**通知；超额 spawn 被**显式拒绝**（不是静默）。

## 配置键实查（不猜键名）

`dsh --profile sdk --dump-config` 里与子 agent 相关的插件行（原文）：

```yaml
- id: subagent
  name: '@deepseek-ai/dsh-subagent'
- id: subagent-spawn-in-process
  name: '@deepseek-ai/dsh-subagent-spawn-in-process'
  config:
    providerName: spawn
- id: subagent-fork-in-process
  name: '@deepseek-ai/dsh-subagent-fork-in-process'

    providerName: fork

  name: '@deepseek-ai/dsh-tool-subagent-control'
- id: tool-subagent-list-agents
  name: '@deepseek-ai/dsh-tool-subagent-control/list-agents'
- id: tool-subagent
  name: '@deepseek-ai/dsh-tool-subagent'
```

深度另一码事：`maxDepth` **不是**插件 config，而是 Host settings 的 `subagent` 段（默认 `1`，= 只许直接子）；本次超限用 `maxActiveSubagents: 1` 触发。

## 实验 C：越额拒绝形态

与实验 A 同一次运行即覆盖：同一 step 内两次 `subagent` 调用，第 1 次成功占位，第 2 次立刻被拒，**不是排队、不是静默、不是挂住**：

```text
Error: subagent limit reached (active child limit: 1); wait for an existing child to finish or complete this work with the current agents
```

注意两套面：**模型可见**的是上面这句人话文本（`tool_result.status=error`）；**服务/协议层**的稳定错误码是 `ACTIVATION_LIMIT_REACHED`
（`dsh-subagent` README：`At capacity, creation or cold resume rejects with ACTIVATION_LIMIT_REACHED`；浏览器侧提示是 `subagent/delivery-unavailable`）。
本探针只实测了人话文本 + `subagent.finished.status`（成功路径），未实测 `status:"error"` 的 finished 载荷。

## 结论

**过**（附一条必须写进规格的限定）——sdk profile 的 JSON-RPC 里 `subagent.started` / `subagent.finished` 实测都发（含 childSessionId、
status、stopReason、lastAssistantMessage）；越额 spawn **显式拒绝**且带 `active child limit: 1` 原文；子 agent 出生/结束在父会话日志里也有
持久事实（`subagent/catalog`、`source=subagent-settled`）与 projcache 投影行。
限定：**headless `--json` 的 run-event 流不携带任何 subagent 生命周期事件**（24 行事件里 0 条 `subagent.*`）——桥不能靠读 headless 输出记账。

## 对规格的含义

1. N1 桥的记账面**必须**是 sdk profile 的 JSON-RPC 通知（`subagent.started|finished` + `session.event`），不能是 `headless --json`；
   目标态 #7 的"`subagent.*` 记账"落点因此是"桥转发 + Host 写 `agent_calls/subagent_*`"，且 `subagent.finished` 自带
   `status/stopReason/lastAssistantMessage`，可直接作为收口证据之一（但仍不得替代 `submit_result`）。
2. Q2 的 `maxActiveSubagents=2` 可落地：键名在 `subagent` 插件 config；超限是**同步显式错误**（不排队），与"父等子不能被自己占位卡死"的
   设计一致；规格里应写明"超额 = 显式失败 + 不重试"而不是"等待"。
3. 子 agent 有独立 session + descriptor ⇒ 看板投影能列出"某个 attempt 起了哪些子 agent、何时起、何时结束"；但 `subagentTiming.settledMs=0`
   在父会话投影里，结束时刻要自己从 `subagent.finished` 或 `subagent-settled` 日志行取。

# P7 自动压缩：是否触发 + 计数/时点能否被读到

## 假设

把 default model 的 `contextWindow` 调小 + 给 compaction 配极小保留预算，能低成本触发一次自动压缩；压缩**既在事件流里可见、也在落盘/投影里可数**。

## 配置键实查（不猜键名）

`@deepseek-ai/dsh-compaction-basic` 的 config（`--dump-config` 原文，默认无 config 段；显式覆盖后为）：

```yaml
- id: compaction-basic
  name: '@deepseek-ai/dsh-compaction-basic'
  config:
    thresholdRatio: 0.55
    headroomTokens: 0
    maxTokens: 4096
    retainTokens: 300
```

触发算式（README 原文）：`floor(min(W × thresholdRatio, W − O − headroomTokens))`，`B` 默认 65536。
**坑（实测）**：窗口一小，`W − O − B` 必为负 ⇒ 必须显式 `headroomTokens: 0` **且**给正的 `maxTokens`（"Zero headroom requires an
explicit positive `maxTokens`"），否则插件在首次使用该路由时抛配置错误。`retainRatio`/`retainTokens` 二选一，且保留预算必须 < 触发点。
另：`maxTokens`（模型路由的请求输出上限）就是算式的 `O`——本例 `W=20000, O=1024, B=0, ratio=0.55` ⇒ 触发点 **11000**。

## 命令（最小复现，直接能过）

```bash
H=<repo>/workspaces/.probe-dsh/slots/p6p7/home
cd "$H/work" && DSH_HOME="$H" timeout 400 $N $DSH --profile headless \
  --patch <repo>/workspaces/.probe-dsh/patch-public.yml \
  --patch <repo>/workspaces/.probe-dsh/slots/p6p7/patch-p7-compact-v3.yml \
  --json "读 <repo>/doc/plans/2026-10-28-three-layer-interaction-alignment.md 全文，然后用 3 句话总结 §6.1 的 P6/P7 判据。"
```

`patch-p7-compact-v3.yml` = `patch-public.yml` 之上覆盖：模型 `contextWindow: 20000`、`maxTokens: 1024`；compaction
`thresholdRatio: 0.55`、`headroomTokens: 0`、`maxTokens: 4096`、`retainTokens: 300`。

## 原始输出（第 4 次运行，成功触发且压缩成功）

headless `--json` 事件类型统计（19 行；**没有任何 compaction 事件类型**）：

```text
      1 "type":"final"
      1 "type":"session"
     10 "type":"status"
      2 "type":"text"
      2 "type":"thinking"
      3 "type":"tool_call"
      3 "type":"tool_result"
```

落盘会话日志（`zstd -dc session-*.jsonl.zstd`，49 行）里的压缩事件原文（`summary`/`rawOutput` 已截断并标注）：


⇒ (a) 压缩**发生了**（1 次 `compaction/summary` = 1 次成功压缩，含 3218 tokens 的 tool-result 剪枝 + 3356 tokens 的被替换区间）；

`shadowedTokenCount` 即释放量；`compactionId` 可把 start/summary/end 三件套配对。
同一 turn 内还有第 2 对 start/end（`compactionRetries` 默认 1 的重试），**失败形态被显式记进 `compaction/end.error`**（没有 summary 事件）——这是可判的失败信号。

## 前两次失败形态（成本与坑，原样记录）

| 尝试 | 配置差异 | `compaction/end` 原文 |
|---|---|---|
| v1 | `retainRatio: 0.1`（=1897 tokens） | `{"error": "summary is not smaller than the shadowed content (422 estimated framed tokens >= 45)"}`（两次：turn 1 / turn 2） |
| v2 | `retainTokens: 300`，但 compaction `maxTokens: 1024` | `{"error": "summarization truncated at the token cap (incomplete checkpoint)"}` |
| v3 | compaction `maxTokens: 4096` | 第 1 对 start→summary→end **无 error**（成功）；第 2 对（重试）`summary is not smaller than the shadowed content (1314 >= 1314)` |

v1 的教训：小窗口下**工具声明本身**就占 ~4899 tokens（`contextBreakdown.toolsTokens`），`contextWindow 20000` 时可用历史只有 ~1.8k tokens，
默认 `retainRatio 0.16/0.1` 会把可压缩头部（只剩 45 tokens）全吃掉 ⇒ 压缩必然"摘要比原文还大"。要小窗口触发压缩必须把保留预算压到接近 0。
v2 的教训：`maxTokens` 是**含 reasoning token 的摘要输出上限**，1024 会被推理吃光并截断 ⇒ 判失败。

## 投影里能不能读到（关键判据）

`storages/session_projcache/sessions/<id>.json` 的行（原文）：

```json
"contextPressure": {"surfaceTokens": 6251, "contextWindow": 20000, "pressureTokens": 14637, "sampledSurfaceTokens": 5634}
"contextBreakdown": {"systems": [{"seq": 7, "tokens": 648}], "surfaceTokens": 6251, "breakdown": {"systemTokens": 648, "toolsTokens": 4899, "messageTokens": 5603}}
"tokenUsage": {"totals": {...}, "last": {...}}
```

行名全集（原文）：`title,titleInput,llmRetry,sandboxMode,goal,tokenUsage,contextPressure,contextBreakdown,todos,turnBoundary,inbox,userQuestions,plan,permissions,workingDirectory,subagentCatalog,subagentTiming,subagent,subagentModelSelectionPolicy`。
**没有 compaction 行**（对整份 projcache 做 `'compact' in json.dumps(...).lower()` ⇒ `False`）。
⇒ 现状：投影能告诉你"压力多少"，**不能**告诉你"压缩过几次"。压缩次数/时点目前只能由 Host 读会话日志的 `compaction/summary` 事件得出（或要求 DSH 新增 projection 行）。

## 落盘解码方法（多帧 zstd，实测）

`session.v4.jsonl.zstd` 是**追加写多帧**：本会话 37229 字节里有 **20 处** `28 B5 2F FD` 魔数命中（偏移 `[0,194,348,794,16520,17387,17616,18992,20341,21550,…]`）。
`zstd -dc <file>` 能一次解出全部帧（实测得到 48/49 行完整 JSONL，无需自己切帧）；若用 Python `zstandard` 的流式 API 需注意 `read_across_frames`/`decompressobj`，
本机 `loop/.venv` **没有** `zstandard` 模块（`ModuleNotFoundError`），只有 `/usr/bin/zstd`。

## 结论

**部分** —— (a) 压缩能被低成本触发且行为可控（过）；(b) 压缩次数/时点在**落盘会话日志**里可读（`compaction/summary` 条数 + `time` + `shadowedTokenCount`），
但 **headless `--json` 事件流里一条都没有**，**projcache 投影也没有 compaction 行**（不过）。
即"压缩可观测"依赖 Host 自己读 session log 或 DSH 补投影，不能指望现成事件流。

## 对规格的含义

1. 目标态 N7/N8 的"压缩次数由 DSH 报告并展示"不能直接拿 `--json` 事件实现：**Host 必须在 attempt 进程内自己落账**
   （读 sdk 侧 `session.event` 里的 `compaction/*`，或读 session log 的 `compaction/summary` 计数），再投影到看板；
   这与 N2 "记录扩压缩次数"的落点一致（`agent_attempts`/投影新增 `compaction:{count,lastAt,freedTokens}`）。
2. P7 判据要写成可机器判的形式："存在 ≥1 条 `compaction/summary`" + "计数出现在投影里"；失败必须按 `compaction/end.error` 显式登记
   （三种失败形态：`summary is not smaller than the shadowed content`、`summarization truncated at the token cap`、配对缺失的 orphan start），
   **不得**把"压缩没触发"当成"压缩成功"。
3. 生产配置约束（要进 SPEC-08 执行器契约）：小窗口 / 需要主动压测时，`headroomTokens`、`maxTokens`、`retainTokens` 必须成套给足，
   否则首次使用该路由即配置错误；`maxTokens` 要覆盖 reasoning，否则摘要截断。
4. 残余风险 C5 的描述可以更新为："DSH 压缩在落盘上可数（`compaction/summary`），但默认不进事件流/投影 ⇒ 需要 Host 主动落账；
   仍无法证明'会话读完了输入包'"。
