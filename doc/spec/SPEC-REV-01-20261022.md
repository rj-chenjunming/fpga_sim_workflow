## R2 闸门材料充分性（G1 材料必须可判）

**问题（实测，2026-10-22，run `RUN-20261022-143532`）**：人工在 G1 时"看不出改了什么"。材料下发的每条差异只有
`entry_id / kind / change / evidence` 等索引字段，`evidence` 是一条长路径字符串；而变更本体
（`before`/`after`、`diff_hunk`）只存在于 run 目录的 `n2_diff.json` 与 `n3_digest.md` 里，界面没有入口。

- `/api/runs/RUN-20261022-143532` 的 `pending_interrupt.payload.difference_items.entries` 只有
  `entry_id/kind/change/unresolved/evidence/lines/offset/segment`，**无 `before`/`after`**；
- `n2_diff.json` 中同一 entry 有 `before`/`after` 原文，但未投影进闸门材料；
- RTL 条目 `diff_hunk=null`，原因是 `sys_reg.v` 为 **GBK** 编码，N2 只按 UTF-8 读取后判"非 UTF-8 ⇒ 无数值 hunk"。

**规范**：[SPEC-01](CHANGE_IMPACT_LOOP_SPEC.md) §7.1 定义逐条最低字段（`before`/`after`/`diff_hunk`/`encoding`/`unresolved`/`drill_fixture`）、
`doc_entry` 与 `rtl_file` 的展示下限、未决条目的逐条处置通道，以及三条禁止（路径代替本体、无 hunk 当作无变化、夹具冒充实测）。
[SPEC-04](WEB_UI_SPEC.md) §4.4/§5 定义双栏 before/after、行级 hunk、变化字段优先、`drill_fixture` 徽标、N3 摘要与 Host 留痕入口。

**验收判据（可判定）**：
1. G1 材料的每条 entry 都有非空 `before` 与 `after`；源文件非 UTF-8 时 `encoding` 非空；
2. RTL 条目要么有 `diff_hunk`，要么有"为什么没有 + 可替代行号证据"；
3. 界面对每条差异渲染 before/after 两栏（截图或 DOM 断言）；
4. drill 运行的材料带 `drill_fixture` 徽标（DOM 断言）；
5. 材料区能打开 `n3_digest.md` 入口（存在性探测，缺失显示"未生成"）。

**未决**：v1 界面缺 `entry_decisions` 逐条输入（[SPEC-04](WEB_UI_SPEC.md) §12 已登记的缺口）。本次只要求"显式提示 + 可复制 API 样例"，是否补界面控件留给实现决策。

> **已关闭（2026-10-26 追记）**：界面控件已由 P-17（2026-10-23）实现 —— 闸门视图按服务端 `entry_decisions_required` 渲染逐条处置控件，见 [WEB_UI_SPEC §4.4](WEB_UI_SPEC.md)。

## R3 非 UTF-8 差异可读（N2 解码策略）

**问题**：GBK 源文件（`RTL/SRC/imports/SRC/reg/sys_reg.v`，46584 B，含 CRLF）被判"二进制/编码不可解"，差异本体在材料里彻底消失；实测按 GB18030 解码后可得 1168 行文本与精确 hunk（`32'h04` → `32'h0000_0004`）。

**规范**：`rtl_file` 条目必须尽量给出文本级差异 —— 先 UTF-8，失败再试 GB18030（GBK 超集），仍失败才允许 `unresolved`；
解码成功时必须在条目里记 `encoding`，行号按原文件。**口径唯一**：解码与比较只允许一套实现，不得出现第二套判据。

**落点与边界**：`kb/tools/n2_diff.py` 属**冻结目录**（[AGENTS.md](../../AGENTS.md) §3）；本次只改 SPEC，
实现须单独变更、单独留证（`kb/README.md` 变更登记 + `_selftest_*` 自测 + 确定性两条判据），不得以"顺手修"方式合入。

**验收判据**：对同一 GBK 夹具重跑 N2，条目带 `encoding`（值为**实际命中的 codec 名**；GB18030 优先，实测为 `gb18030`）且 `diff_hunk` 非空；对真正的二进制文件仍保持 `unresolved`（不因放宽解码而误判）；同一 `--now` 两次运行输出逐字节相同。

## R4 节点可点击（**全部节点**：N0–N16 + 内部节点 + HALT）

**问题**：执行视图的节点 chip 不可点击（纯 `div`，无 click/tabindex）；人只能看到"N1 完成"这类状态，看不到该节点**执行了什么、结果是什么、证据在哪**。

实测（2026-10-22，run `RUN-20261022-143532` 与源码核对）：
- **全部节点**都不可点，不只是 N1/N2；
- `node_history` 只含 `{node,status,kind,at,detail}`，**`refs` 只在事件顶层**（构造 `node_history` 时丢弃）；
- **没有任何节点有 `summary`**；`source` 只有 N1/N2/N5/N6 等部分节点有（N0/N7/N9/N15/N16/闸门节点没有统一口径）；
- 各节点 detail 完整度参差：N0 `{mode,fixture_files,gate_init_rc}`；N5 有 `must_change`/`index_gaps`；N9 `{cases,koutou1,koutou2}`；闸门 `{gate,decision,branch,actor}`；`HALT` 只有 `reason`；
- 内部节点（`N6_apply`/`N9_submit`/`N15_select`/`N15_submit`）在四段流程之外，当前只以"未纳入四段展示的节点"列出，同样不可点；
- 单节点详情端点不存在（`GET /api/runs/{id}/nodes/{node}` 全仓零命中）；现有 `GET …/agents/{node}` 对 Host 节点直接 404（只覆盖 N3/N6/N8/N10/N11/N12）。

**规范**：[SPEC-02](LOOP_ORCHESTRATION_SPEC.md) §10.4 定义**全节点**执行详情投影：范围不按白名单裁剪（含内部节点、HALT、未来新增节点、未知节点）；
每个节点 `detail` 必含 `source` + `summary`；给出**逐节点下限表**（N0–N16 + 内部节点 + HALT）；status 原值语义（闸门=决策值、N8/N11/N16/HALT 非 ok/failed）；
失败态不得记成完成、缺失列 `missing_fields`、旧 run 不回填。
[SPEC-04](WEB_UI_SPEC.md) §4.2.1 定义节点详情面板（五区块，适用于全部节点），§6.7 定义只读端点（未知 node 返回 `known=false` 而非 404）。

**实现约束（验收时会核）**：
1. 端点之外**必须同时补 detail**：`host_steps.py`、`model_steps.py`、`long_jobs.py`、`gates.py` 里**每一处** `node_finished` 都要按 §10.4 逐节点表补 `summary`/`source`（及 N1/N2 的摘要与统计）——只加端点满足不了字段下限；
2. 面板用**独立弹层/抽屉**（自带状态），不得做成 chip 内联块：执行视图流程条约 1.5 s 全量重建，内联块会被轮询清掉；
3. 历史 run **不回填**：旧 run 缺新字段时列 `missing_fields` 并显示"未下发"，验收不得拿旧 run 的缺失当缺陷、也不得改历史事件；
4. 状态不得归一：面板照服务端原值显示，`refused`/`broken`/`escalated`/`halted`/闸门决策值都不得被前端折叠成"完成"或"失败"。

**验收判据**：
1. 分别点开一个 Host 节点（N1）、一个模型节点（N3）、一个闸门节点（N4）、一个内部节点（`N9_submit`）与 `HALT`，五个区块都齐全、都能读到该节点的事件切片；
2. 每个节点都能看到 `source` 与 `summary`（新 run）；N1 显示 manifest 摘要、N2 显示三路统计与逐条 before/after；
3. drill 运行所有节点标注 `drill_fixture`；`refs` 缺失时显示"证据缺失"（`/evidence/exists` 探测）；
4. 面板不新增写动作（现有四个业务写动作不变）；
5. 前端不自行拼装事件：数据来自 §6.7（实现前允许从 `node_history` + `/events` 组装，但字段与 §6.7 一致）；
6. 未知/未来节点也能打开（`known=false` 空投影 + 原始事件），不 404、不静默不可点。

## R5 S0 与 drill 的关系（环境搭建能不能验证到）

**问题（实测）**：用户问"环境搭建在 drill 模式有没有体现、后来改的『先 copy 再替换』能不能验证到"。
查证结论是 **不体现、验证不到**：

- `loop/workflows/main_flow.py` 与 `loop/workflows/chunks/host_steps.py` 中 **没有任何 S0 调用**（`grep -n "s0\|S0"` 无命中）；
- drill 的 N0 只把冻结夹具文件复制进 run 目录，不复制环境、不替换 RTL；
- "先 copy 再替换"实现在 `loop/host/s0.py`（`shutil.copytree` + 删旧 RTL + `copytree` 新 RTL，带四项 checks 与基线零写入见证），
  通过 `POST /api/s0` 独立驱动，与 N0–N16 无拓扑连接，工作台只能从"环境准备"视图单独操作。

**规范**：[SPEC-05](S0_ENVIRONMENT_SPEC.md) 新增 §6：S0 不是 N0；run 必须带可空 `s0_record_id`；drill 不覆盖 S0；
`ready_for_execution` 当前恒 false 且不被运行入口消费（S0-b 未接入，不得作为准出）；若将来接入必须是显式选项
（如 `s0_rehearsal`），不得改拓扑与三闸门。定义 **S0-rehearsal**（临时小基线，软件能力验收）与
**S0-real**（内网真实环境，另行验收）两级；给出"先 copy 再替换"的五条可复核判据（copy/rtl/non_rtl/baseline + 失败保留记录）。
[SPEC-04](WEB_UI_SPEC.md) §4.5 定义运行视图的环境来源徽标（`S0 记录 <id>` / `未经 S0 派生`）。

**验收判据**：
1. run 视图中 drill 运行显示"未经 S0 派生（drill 不覆盖 S0）"；
2. 一次 S0-rehearsal 记录四项 checks 全 `passed`，且基线前后清单一致；
3. 失败路径（如非 RTL 污染/已有目标）产生 `failed` 记录并保留，不被静默覆盖；
4. 证据里明确区分 rehearsal 与 real，未跑 S0-real 时标"未跑"。

**不在本次范围**：把 S0 并入 N0–N16 拓扑；实现 S0-b；用 drill 结果替代 S0 验收。
