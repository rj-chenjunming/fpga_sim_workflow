## R1 节点详情面板：人话优先 + 原始日志收起

**问题（实测，2026-10-23 用户走查）**：节点面板一打开先看到「身份」技术键值、再看到按 `seq` 倒序的
事件流水（`#35 node_finished N9 fail …`）和整张 `detail` 原始表格（`cmd` / `stderr_tail` / 绝对路径…）。
用户不知道 `seq` 是什么、也不知道这个节点到底做了什么、结果如何。**可读性差不是信息少，而是顺序与层次不对。**

**规范**：面板从上到下固定六块（适用全部节点，含内部节点、`HALT`、未知节点）：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| ① 头部 | 节点号 + 名称 + owner + **状态原值** + 执行方式 | `node` / `name` / `owner` / `status` / `source` |
| ② 这一步做什么 | 一句话用途（服务端目录下发；未知节点显示"服务端未登记用途"） | `story.purpose` |
| ③ 结果一句话 | `summary` 原文（缺失显示"未下发"） | `summary` |
| ④ 关键数字 | 逐节点精选字段（中文标签 + 值；缺失逐项"未下发"） | `story.key_results` |
| ⑤ 过程 | 按事件顺序的人话步骤（不含 `seq`；时间由前端按 `ts` 渲染） | `story.steps` |
| ⑥ 证据 / 失败 | 本地现状（存在性探测 / 失败时 error 原文） | `refs` / `events` |
| ⑦ 原始记录（排查用） | **默认收起** `<details>`：原始事件切片（含 `seq`、`kind`、`status`）、完整 `detail` JSON、`missing_fields`、身份技术字段 | `events` / `detail` / `missing_fields` |

- **`seq` 说明**：同一 run 内严格递增的事件流水号，只用于排序和定位（"第几条事件"），**不是业务状态**。
  面板正文不再出现 `seq`；只在 ⑦「原始记录」里保留，并在该区顶部写明这句解释。
- **步骤生成是投影、不是判定**：`story.steps` 由服务端按事件 `kind` 白名单 + 事件 `detail` 现有字段
  确定性拼出人话；缺字段就写"未下发/原因未下发"，**不推断、不换算、不排序材料**。
- **未知节点**：`purpose=null`、`key_results=[]`，步骤仍按事件生成；界面显示 `known=false` 的现有警示。
- **drill 的措辞**（用户反馈"夹具好抽象"）：`source=drill_fixture` 在面板显示为
  「drill 演示数据（不碰真实环境）」；首屏 ②下方固定一行说明「节点结果来自预置数据（夹具），
  不碰真实环境，也不验证环境搭建（S0）；要验证环境搭建请用环境准备视图」。N0 的 `fixture_files`
  在 real 模式显示「0（真实运行不复制预置文件）」，drill 显示实际份数。
- **节点未收尾**：`detail` 为空（还没有 `node_finished`/`node_failed`）时，④ 只显示一行
  「该节点还没有收尾记录（detail 为空），关键数字等它跑完再看」，**不**逐项堆"未下发"；
  `detail` 非空但个别字段缺失时，仍逐项显示"未下发"。
- **失败**：`node_failed` 时 ⑤ 的最后一步为失败原文摘要，⑥ 显示 error 原文；全文不得出现"完成"。

**逐节点"一句话用途 + 关键数字"清单（服务端 `NODE_CATALOG` / `KEY_FIELDS` 的权威内容）**：

| 节点 | 一句话用途（面板 ② 原文） | 关键数字（面板 ④ 字段 → 标签） |
|---|---|---|
| N0 | 把这次运行要用的工作目录准备好，并把闸门/基线状态初始化。 | `baseline` 基线 · `mode` 运行模式 · `fixture_files` 拷入预置文件（real 显示"0（真实运行不复制预置文件）"） · `gate_init_rc` 闸门初始化退出码 |

**验收判据（可判定）**：
1. 打开任一节点，首屏能读到"这一步做什么 / 结果一句话 / 关键数字 / 过程"，**不必展开**；
2. 正文（③–⑥）不出现 `seq` 字样；⑦ 默认收起，展开后能看到逐条事件的 `seq` 与完整 `detail`；

4. 缺失字段在 ②–⑤ 逐项显示"未下发"，不补默认值；失败节点全文不出现"完成"；
5. 未知节点面板不报错（`known=false` 警示仍在），步骤按事件生成；
6. 面板仍只读：点击/刷新/展开不产生任何 POST。

## R2 闸门节点：二级差异清单 + 勾选处置（**待走查确认，暂不实现**）

> 用户 2026-10-23 走查 N4 的原话：「这个节点需要好好修订 应该把差异点一个一个列出来 并且有勾选的地方
> 做成二级的形式 比如说一个修订点 第一级先说明什么修订 然后点开有两列详细的前后对比可看」。

**范围**：闸门节点 `N4`（G1 差异确认）先做；`N13`（报告验收）/`N14`（回归决策）的"待确认项"来源另议，
但沿用同一交互骨架（二级折叠 + 逐项处置 + 提交）。

### R2.1 交互

1. 面板在「结果」之后新增「差异清单（共 N 条修订点，已处置 M 条）」区，每条一行（一级）：
   - **勾选框**（处置状态）；
   - 一句话说明"这条改了什么"（优先取 N3 摘要/字段；拿不到写"缺一句话说明"，不编）；
   - 定位：文件名 + 行号/偏移 + 变更种类 + 是否未决（未决用醒目样式）；
   - 「查看前后对比 ↗」入口。
2. **前后对比用浮窗，不在列表行内展开**：列表行保持紧凑；点入口打开**浮窗**（宽 ≥ 80% 视口、可滚动；
   代码行默认自动换行，避免窄窗截断），浮窗内：
   - **左右两栏 before / after**（全宽）：行级 hunk 标行号；`doc_entry` 先列变化字段（before→after），
     其余折叠；无 hunk 时必须显示**原因**（旧版正文缺失 / 非 UTF-8 / 二进制）与可替代证据（行号、md5），不得留空；
   - 元信息：`offset`、`encoding`、`evidence`（md5 变化）、夹具徽标；
   - **逐条处置**：已确认 / 忽略（理由必填）/ 有疑义（理由必填）。
3. **勾完统一提交**：勾选与理由只写进共享 `gate-session` 草稿（按 `run_id + gate + cycle` 身份，不落盘），
   不在节点面板另设提交按钮；底部只显示「已处置 M / N」+「去闸门视图确认并提交 →」，
   **提交入口只有闸门视图现有表单**（操作者 `human:xxx`、理由、签署都在那里，避免两套提交）。
4. **md5-only 变更不计入修订点**：`allfile`（整文件指纹、无文本 hunk）且同一文件已有 `rtl_file`
   文本证据的条目，只作为主条目的**附证据**展示（"另有整文件指纹 1 条（不计入）"），不清单行、
   不计入"N 条修订点"；原值仍在原始记录。
5. **待决策（waiting）**：可勾选、可填理由、可跳去提交；**已决策**：只读展示当时逐条处置
   （来自 `gates.json`），不提供改写入口。

### R2.2 勾选与提交语义（2026-10-23 已定）

- 勾选 = `confirmed`（已确认）；忽略/有疑义必须给理由；**本地勾完统一提交**（不逐条即时提交）。
- 闸门决策由逐条处置推导：有 `disputed` ⇒ 整门 `disputed`；否则有 `ignored` ⇒ 整门 `ignored`；
  否则 `confirmed`。该推导**必须**复用服务端 `gates.normalize_entry_decisions`，前端不另写判据。
- **冗余条目按主条目同处置自动带上**（用户选定方案 b）：服务端在材料投影里给
  `allfile` 条目一个只读标记 `redundant_of=<主条目 entry_id>`；界面提交时按主条目的处置
  自动填充该条目，**仍然覆盖全部 `entry_id`**，服务端校验规则不变（不新增判据）。
- 提交复用现有 `POST /api/runs/{run_id}/gates/{gate}/decision` 的 `entry_decisions` 字段，
  **不新增写动作**；界面只是补上 §4.4/§12 已登记的"逐条处置输入通道"缺口。
