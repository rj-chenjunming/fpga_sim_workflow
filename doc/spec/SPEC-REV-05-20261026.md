## 2 R1 · 失败报告收口通道

### 2.1 问题（契约自相矛盾）

```
N9 全跑失败（口径一≠0）
      │
      ▼
N10 对账：verdict_passed=False
      └─ case_states：5 个用例 → "已修订待验"（不得称跑通）
      │
      ▼
G2：accept 前置 = I2「待验=0」
      └─ 待验 = 5 ≠ 0  ⇒  accept 永远被拒
      │
      ▼
用例只能由"通过"推进到"已验证通过"，失败轮没有出口
      ⇒  N16 不可达；唯一可选 rework（再跑 21 h，结果相同）
```

**不变量冲突**：I2 的本意是"待验不得称跑通"（防止把没验的当通过），但它的实现方式
（"待验=0 才允许 accept"）把"接受一份**未通过**报告"也一并禁掉了。

### 2.2 方案 A：新增闸门决策 `accept_failed`

- G2 多一个决策值（`kb_lib.GATE_DECISIONS["G2_report_accept"]` 增加 `accept_failed`）；
- 前置改为：`N12 报告存在 ∧ claimed_verdict=not_passed ∧ 非空 reason`，不再要求 I2 清零；
- `accept_failed` 只表示"人已阅失败报告并收口"，**不等于**判据通过；N16 仍被 I3/I4 拦。

| 优点 | 缺点 |
|---|---|
| 语义最明确：接受的是"失败报告" | 要改 `kb/tools/**`（**冻结目录**，需单独授权与评审） |
| 不动用例状态机 | 闸门枚举变更影响：`gate.py` 校验、前端按钮、既有闸门历史兼容、`accept_v1` 断言 |
| 报告与判据彻底分离 | 需要新增 UI 选项文案与 `requires_reason` 规则 |

### 2.3 方案 B：用例终态新增「已验证失败」

- `case_states` 增一个终态：`已验证失败`（跑过、有证据、判据未通过）；
- N10 对"已跑且 `verdict_passed=False`"的用例写 `已验证失败`，不再留在 `已修订待验`；
- **I2 判据不变**（只统计"待验"）：失败轮待验 = 0 ⇒ `accept` 可用；
- `accept` 语义不变（接受报告）；报告仍写 `not_passed`；N16 仍被 I3（口径一≠0）/I4（冲突）拦。

| 优点 | 缺点 |
|---|---|
| **不动 kb 冻结目录**（改的是软件层状态机与 N10 写入） | 需定义"已验证失败"与"已验证通过"的迁移规则与审计字段 |
| I2 的原始目的更准确：失败用例不再是"待验" | 需要 `case_state.py` 允许该状态（若状态枚举在 kb 则同 A 的冻结问题，**需先查证**） |
| 失败轮闭环自然成立，rework 仍是人的选择 | 报告/工单语义要说明"接受失败报告 ≠ 发版" |

> **实测结论（2026-10-26 已查）**：状态枚举就是 `kb/tools/case_state.py:57` 的固定四态
> `("未改", "已修订待验", "已验证通过", "已退回")`，SPEC-01 I2 也把它写成固定字面量。
> ⇒ 方案 B **必须改冻结目录**，成本高于预期；这也是把 D 列为首选的原因。

### 2.4 方案 D：失败报告的 `accept` 需显式理由（**推荐**）

**不改状态机、不改闸门枚举**，只改 G2 的 accept 前置（纯软件层 `gates.py`）：

- 报告结论为 `not_passed` 时：`accept` 允许，但**强制非空 reason**（人已阅失败报告并收口）；
- 报告结论为 `passed` 时：`accept` 仍要求 I2「待验=0」（原语义完全保留）；
- `rework` 语义不变；
- N16 仍被 I3（口径一≠0）/I4 拦 —— accept 只表示"收到并接受这份未通过报告"，**不等于判据通过**。

| 优点 | 缺点 |
|---|---|
| **完全不碰 `kb/tools/**` 冻结目录**（I2 四态、闸门枚举都不动） | 需明确"接受失败报告"的措辞，避免被误读成通过 |
| 改动面最小：`gates.py` 一个分支 + `contracts.py` 阻断文案 + UI 提示 + 测试 | 需要 reason，等于要求人写下收口依据（这其实是优点） |
| 历史 run 无需迁移（只影响新提交） | 若产品坚持"失败也应有个正式终态"，仍需将来做 B |

### 2.5 方案 C：去掉 `accept` 的 I2 前置（**不推荐**）

把 G2 的 accept 当成"收到报告"，完全放开 I2。改动最小，但会让 I2 失去唯一执行点，
等于承认"待验也能被接受"，与本仓红线（待验不得称跑通）冲突。

### 2.6 四案对比

| 维度 | A `accept_failed` | B `已验证失败` | **D 失败报告+理由** | C 放开 I2 |
|---|---|---|---|---|
| 改 `kb/tools/**` 冻结目录 | 是（闸门枚举） | **是**（I2 固定四态在 `case_state.py:57`） | **否** | 否 |
| 改动面 | 中（枚举+UI+前置） | 大（状态机+N10+报告+UI） | **小（G2 前置+文案+测试）** | 小 |
| 语义清晰度 | 高 | 高 | 高（接受≠通过） | 低 |
| 对 drill/accept_v1 影响 | 大（枚举断言） | 中 | **小** | 小 |
| 风险 | 闸门历史兼容 | 状态迁移与审计、旧 run 语义分叉 | 需把接受失败报告的措辞写清楚 | 破坏 I2 初衷 |

### 2.7 影响面清单（以 D 为例）

| 落点 | 改动 |
|---|---|
| `doc/spec/CHANGE_IMPACT_LOOP_SPEC.md` §5 I2/G2 行 | 明确「accept 接受的是报告结论」与「待验不得称跑通」两条并存（本文件批准后回填） |
| `doc/spec/LOOP_ORCHESTRATION_SPEC.md` N13/G2 | accept 前置的两分支说明 |

| `loop/services/contracts.py` | I2 阻断文案区分「报告未通过 / 其余」；`can.judge_pass` 语义不变 |
| `loop/web/*` | 理由输入提示、按钮可用性（不做新写动作） |
| 测试 | 失败轮 accept 成功（有理由）、空理由仍拒、未通过报告 accept 后 N16 仍拒、`passed` 轮行为不变 |

### 2.8 验收判据（可判定，以 D 为例）

> **实现落点（2026-10-26）**：`loop/workflows/chunks/gates.py` G2 `accept` 分支（`not_passed` ⇒ 强制 reason；
> 其余仍走 I2）；`loop/services/contracts.py` 新增 `report_claimed_verdict()`（从 `n12_report.md` 读，
> 缺失即 `None`、不猜）并让 I2 阻断文案区分结论；`loop/web/app.js` 在 G2 显示"未通过 ⇒ 接受需理由"提示，

> 无报告不推断），**39 passed**。契约已回填：[SPEC-01](../../doc/spec/CHANGE_IMPACT_LOOP_SPEC.md) §1 I2 增补与 §11 第 7 项。

1. 构造一个"全跑失败"的 run：`accept` 返回 200，`gates.json` 记 `human_signed=true`；
2. 同一 run 若仍有"待验"用例 ⇒ `accept` 仍 403（I2 未被削弱）；

## 3 R2 · 把本轮真实轮冻结为 drill 夹具

### 3.0 直接回答：可以，而且这就是既有机制；但建议「新增 + 参数化」，不建议直接取代

- **可以**：`FIXTURE_RUN` 本身就是"一个真实轮的冻结"（见 3.1），本轮把 `RUN-20261024-002609`
  冻进去，drill 就会带着"4 文件改动 / 5 用例 / 口径一 1716 / 印记不一致 / G2 被 I2 拦"的真实形态；
- **不能零改动**：① 夹具 id 目前是硬编码常量；② drill N9 只回放**单个**固定日志
  （`_REAL_CASE = "tc_pcie_rw_02"`），要演"5 例"必须把 N9 泛化成按用例回放；
- **不建议取代旧夹具**：`accept_v1_run.sh` 的断言依赖旧夹具的"单例 + 1687 + 死任务"形态，
  直接替换会让端到端基线失效；应做成两套夹具 + 选择开关（缺省旧夹具）。

### 3.1 既有设计事实

现行 `FIXTURE_RUN` **本来就是"一个真实演练轮的冻结"**，代码注释写明了选择理由
（覆盖双计数分歧 1687 vs 0、死任务、印记 1/1/1、闸门拒绝、篡改检测、staging 残留），
并明确"真实全跑单用例 ≈19 min、修订后可达 22.8 h，不能作为交互开发循环"。

⇒ 用户的想法（把本轮 real 冻结成 drill）**不是新机制，而是把夹具换成更贴现在的真值**。

### 3.2 目标与命名

| 项 | 建议 |
|---|---|
| 新夹具 id | `RUN-20261024-002609`（直接以真实 run id 命名，保留可追溯性） |
| 形态 | `WORKSPACE/runs/RUN-20261024-002609` 的**只读快照**（chmod 444 + md5 清单） |
| 选择方式 | `FIXTURE_RUN` 参数化：`LOOP_DRILL_FIXTURE=<run_id>`（缺省仍指旧夹具） |
| 保留旧夹具 | **保留**（`accept_v1_run.sh` 断言依赖其"单例 + 1687"形态） |

1. **夹具参数化**：`loop/workflows/context.py` 的 `FIXTURE_RUN` / `FIXTURE_EVIDENCE_LOG` 改为

   必须有 `n1/n2/n5/n12 + evidence`，缺就**显式失败**（不得回退到旧夹具静默继续）。

   要演示"本轮 5 例"，需：

   - 逐例复制对应 `*_run.log` 与三库日志；
   - 逐例产出 `n9_run_summary.tsv` 行 + 逐例计数（Host 聚合，**不重算口径**）；
   - 生成"drill 夹具来源"归档说明（沿用现有 `DRILL_FIXTURE_PROVENANCE.txt` 机制）。
3. **`DRILL_FILES` 扩展**：在现有 12 项基础上，按新夹具实际需要的文件增补（只增不改）。
4. **回归**：`accept_v1_run.sh`、`test_*` 的 drill 期望必须显式区分"legacy 夹具 / real-20261024 夹具"，
   不得一套断言套两套夹具。

### 3.6 边界（不得声称）
