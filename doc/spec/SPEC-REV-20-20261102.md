## 0 一句话

机器判据**一字不改**；人看过机器列出的失败原因后，可以**签一条带理由的覆写记录**，把该用例状态写成
`已验证通过`，从而解除 I2、让本轮能继续收口/晋升。**覆写是显式的人签例外，必须在每一处显示**。

## 1 要解决的事实（为什么需要）

真实轮 `RUN-20261024-002609`（5 例、21.56 h，见 [REAL_N9_20261024](../evidence/REAL_N9_20261024.md)）：
N9/N10 判 5 例全未通过（口径一合计 1716、4 例印记值不一致），用例停在「已修订待验」⇒
I2 让 G2 的 `accept` 永久被拒 ⇒ N16 不可达。

其中 `tc_pcie_rw_smoke` / `tc_rtc_05` / `tc_rtc_10` 三例**口径一 = 0、UVM_ERROR = 0**，只因
**观测点印记的期望值**（来自旧文档条目）与实测不符而判失败。这类失败是否该拦本轮，需要人判断：
判据没有错，但"这一次"的期望值/上下文可能不符合人的预期。现有机制只有"整轮接受失败报告"
（SPEC-REV-12 方案 D），**无法把个别用例放行**，也无法让本轮走到晋升。

## 3 数据契约

### 3.1 `case_states.json` 条目新增字段（只增，旧记录兼容）

```json
{
  "case": "tc_rtc_05",
  "state": "已验证通过",
  "updated_by": "human:chenjunming",
  "updated_at": "2026-11-02T11:00:00+0800",
  "overrides": [
    {
      "schema": "kb/case_override",
      "action": "pass",
      "actor": "human:chenjunming",
      "actor_kind": "human",
      "reason": "期望值来自旧文档条目；实测值与本变预期一致，属期望过期",
      "decided_at": "2026-11-02T11:00:00+0800",
      "prev_state": "已修订待验",
      "machine": {
        "schema": "loop/n10_cases",
        "source_path": "n10_cases.json",
        "source_md5": "…",
        "passed": false,
        "criterion": "PASS ⟺ 两套口径皆 0 ∧ UVM Report Summary 出现 ∧ 期望观测点印记三向一致",
        "reasons": ["印记 N6_pcie_test_tc_rtc_05 三向不一致：['value_matches_expected']"],
        "counts": {},
        "imprints": {},
        "evidence": {"path": "evidence/20261024-003330_tc_rtc_05_1_run.log", "md5": "…"}
      },
      "record_sha256": "sha256(canonical(record 去掉 record_sha256))"
    }
  ]
}
```

- `state` 是**读侧唯一事实**；`overrides[]` 是 append-only 审计链。
- 生效规则：最后一条 `action="pass"` ⇒ `state="已验证通过"`；最后一条 `action="revoke"` ⇒
  `state="已修订待验"`。`prev_state` 记录动作发生前的状态。
- 撤销也**追加**一条（`action="revoke"`），不删除、不改写前面的记录。
- **撤销的语义边界（2026-11-02 裁定）**：`revoke` 只用于"撤回我自己刚签的覆写"——
  必须存在最近一条 `action="pass"` 的覆写记录。**不得**用 `revoke` 把"机器判定通过/正常流程写入的
  `已验证通过`"降级成 `已修订待验`（那等于人凭空制造待验、阻断本轮，且违反 O-1/O-3 的精神）。
  最近一条覆写记录不是 `pass` ⇒ 拒绝（rc=3 / 403），台账不动。
- 台账 `writer`/`updated_by` 同步写 `human:<name>`（与既有字段同形）。

### 3.2 机器原因的唯一来源：`<run_dir>/n10_cases.json`（新增产物，N10 Host 落盘）

```json
{
  "schema": "loop/n10_cases",
  "run_id": "RUN-…",
  "created_at": "…",
  "criterion": "聚合判据 = 各用例 I3 判据的合取（含印记三向一致）",
  "cases": {
    "tc_rtc_05": {
      "case": "tc_rtc_05",
      "passed": false,
      "criterion": "PASS ⟺ 两套口径皆 0 ∧ UVM Report Summary 出现 ∧ 期望观测点印记三向一致",
      "reasons": ["印记 … 三向不一致：['value_matches_expected']"],
      "counts": {"koutou1": {"value": 0}, "koutou2": {"value": {"UVM_ERROR": 0, "UVM_FATAL": 0}}},
      "imprints": {"N6_…": {"consistent": false, "checks": {"value_matches_expected": false}}},
      "evidence": {"path": "evidence/…_run.log", "md5": "…", "bytes": 123456}
    }
  }
}
```

- **只搬运已算好的判据**（`n9_result.cases[*].verdict` 与 `counts`/`imprints`），Host 不重算、不判新东西。
- `evidence.md5` 由 Host 在落盘时对权威 `run.log` 计算（身份可复核）。
- **落盘失败策略（2026-11-02 裁定）**：写 `n10_cases.json` 失败 ⇒ 记一条**显式 warning 事件**（并在
  N10 result 里可见），**不把 N10 判失败**（该产物缺失的后果是"本轮不可覆写"，由服务层 fail-closed 拒绝）。
  不得静默吞异常，也不得用默认值伪造产物。
- 旧 run（本规格之前）没有该文件 ⇒ **显式拒绝覆写**（不解析 `n10_reconcile.md`，不做第二套解析）。
  界面文案：「该轮机器原因未留存（早于覆写功能），不能盲签」。

### 3.3 schema

`kb/schema/case_states.schema.json` 条目属性新增 `overrides`（`array`，每项含上表字段；
`action` 枚举 `["pass","revoke"]`，`actor_kind` 枚举 `["human"]`）——**冻结目录单独变更 + 留证**
（先例：`G1_no_impact`，见 [KB_GATE_NO_IMPACT_20261030](../evidence/KB_GATE_NO_IMPACT_20261030/README.md)）。

## 4 前置与拒绝矩阵（全部在写盘前判；拒绝 ⇒ 台账一字节不动）

| # | 场景 | 结果 | rc / HTTP | 台账 |
|---|---|---|---|---|
| 1 | `--actor` 不是 `human:<非空名>` | 拒绝 | 3 / 403 | 不动 |
| 2 | `reason` 空/全空白 | 拒绝 | 3 / 403 | 不动 |
| 3 | 用例不在台账 | 拒绝 | 3 / 403 | 不动 |
| 4 | 当前态不是 `已修订待验`（pass）；或 revoke 时当前态不是 `已验证通过`、**或最近一条覆写记录不是 `action="pass"`**（即该通过并非来自覆写） | 拒绝 | 3 / 403 | 不动 |
| 5 | `n10_cases.json` 缺失 / 用例缺失 / `passed != false` / `reasons` 为空 | 拒绝 | 3 / 403 | 不动 |
| 6 | run 状态不是等待闸门（running/终态） | 拒绝（服务层） | 403 | 不动 |
| 7 | 批量里任一例不满足 ⇒ **整批拒绝**（全有或全无） | 拒绝 | 403 | 不动 |
| 8 | `overrides[]` 的 `record_sha256` 复核失败（`--verify`） | 拒绝 | 4 / 409 | 不动 |

拒绝理由必须写明**具体哪一条不满足**（不写"参数错误"）。

### 6.1 「能不能签」的投影（前端唯一判据来源，2026-11-02 裁定）

`run_view.case_override` 与 `gate_material.case_override` 同形，**由与写端点前置同一函数计算**
（参数化 `action`，不得两套判据）：

```json
{
  "enabled": true,
  "blocked_reason": null,
  "cases": {
    "tc_rtc_05": {
      "state": "已修订待验",
      "machine_present": true,
      "actions": {
        "pass":   {"available": true,  "blocked_reason": null},
        "revoke": {"available": false, "blocked_reason": "当前态不是「已验证通过」"}
      }
    }
  }
}
```

- `enabled=false` ⇒ 所有动作不可用；`blocked_reason` 用人话写明（run 状态 / 缺件）。
- `n10_cases.json` 缺失 ⇒ `enabled=false`，`blocked_reason="该轮机器原因未留存（早于覆写功能），不能盲签"`。
- 前端只消费这些字段；服务端未下发 ⇒ 按钮禁用并明说"服务端未下发可覆写判定"，不得兜底猜。

## 7 接口

`POST /api/runs/{run_id}/cases/override`

```json
{"action": "pass" | "revoke", "cases": ["tc_rtc_05", "tc_rtc_10"],
 "actor": "human:chenjunming", "reason": "……"}
```

- 200：`{"ok": true, "action": "...", "results": [{"case": "...", "state": "已验证通过"}],
  "case_waivers": {...}, "warnings": [...]}`
- 400：请求体形状不对（`cases` 空 / 非数组 / `action` 不在枚举）
- 403：前置不满足（§4 的 1–7），体里带 `detail.error` 与 `detail.blockers`（同闸门端点风格）
- 409：台账与 `n10_cases.json` 不一致到无法判定（或缺件），`detail.reason` 明说缺哪件

## 8 界面契约

1. **G2/N13 闸门面板**：逐用例表新增两列 ——「机器原因」（`reasons` 原文，不翻译、不截断成结论）
   与「操作」（`认定通过` 按钮；非 `已修订待验` 或原因缺失时禁用并给原因）。
2. 点按钮 ⇒ 二次确认弹窗：**原文展示机器原因 + 证据件路径 + md5**，必须填理由才能提交；
   弹窗明确写「这是人签例外，会记入台账，报告仍显示本轮未通过」。
3. 用例列表/报告页/N16 面板：出现 `人签豁免` 徽标（含 actor 与日期），**不得**显示为普通通过。
4. 撤销入口与覆写同处；终态 run 上按钮禁用并显示「本轮已结束，不可撤销」。
